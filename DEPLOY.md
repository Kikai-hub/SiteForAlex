# Деплой Adana Pizza

Сайт разворачивается в Docker: контейнер с приложением (Next.js под PM2 —
по воркеру на каждое ядро CPU), контейнер PostgreSQL (данные), контейнер
Redis (общий кеш меню/промокодов и rate-limit — см. `cache-handler.js` и
`lib/rateLimit.ts`), контейнер с Caddy (обратный прокси + автоматический
HTTPS) и именованные тома для данных Postgres, Redis и загруженных фото
блюд.

**Меню грузится само при первой установке.** В `prisma/seed-data/` лежит
готовый снимок текущего меню (категории, блюда, размеры/цены, допы, фото) —
при самом первом запуске (пустая база) он подхватывается автоматически, и
руками переносить 60+ блюд не нужно. При каждом следующем деплое/перезапуске
этот шаг проверяет «есть ли уже хоть одна категория» и, если да, ничего не
трогает — так что все изменения администратора в панели (новые блюда,
правки цен, удаления) никогда не откатятся и не затрутся автообновлением.
Если позже захочешь обновить сам «стартовый» снимок (например, после того
как собрал ещё более полное меню локально) — `npx tsx
scripts/export-menu-snapshot.ts` пересоздаст `prisma/seed-data/` из текущей
локальной базы; на уже развёрнутый сервер это не повлияет, только на новые
установки с нуля.

## Требования к серверу

- Linux VPS (Ubuntu/Debian — скрипт установки заточен под них; на другом
  дистрибутиве Docker нужно поставить вручную) с root/sudo-доступом по SSH.
- Открытые порты 80 и 443 (сайт слушает только их — контейнер приложения
  наружу не торчит, см. «Почему нет прямого порта» ниже).
- Минимум 2 ядра CPU / 2 ГБ RAM для теста; для реальной нагрузки — от 4
  ядер / 4 ГБ. `web` по умолчанию поднимает один PM2-воркер Next.js **на
  каждое ядро** (`WEB_CONCURRENCY` в `.env` — задать конкретное число вместо
  этого, если сервер общий с чем-то ещё), плюс Postgres и Redis рядом — на
  1-ядерном хосте с 512 МБ RAM все воркеры будут конкурировать за одно и то
  же ядро без выигрыша от кластеризации.

## Установка на чистый сервер — одна команда

По SSH на сервере:

```bash
curl -fsSL https://raw.githubusercontent.com/Kikai-hub/SiteForAlex/main/scripts/install.sh | sudo bash
```

Уже есть домен, указывающий на этот сервер? Передай его сразу — тогда HTTPS
поднимется автоматически в рамках этой же команды:

```bash
curl -fsSL https://raw.githubusercontent.com/Kikai-hub/SiteForAlex/main/scripts/install.sh -o install.sh
SITE_DOMAIN=yourdomain.ru sudo -E bash install.sh
```

**Без домена сайт-витрина (меню, заказ гостем) работает сразу по HTTP**, но
вход в админку/личный кабинет/кабинет курьера — только по HTTPS (сессионные
куки помечены `Secure` намеренно, это не баг). Пока домена нет — эти разделы
подождут, пока не выполнишь шаг из раздела «HTTPS с доменом» ниже.

Скрипт сам:
1. поставит Docker, если его нет;
2. склонирует репозиторий в `/opt/adana-pizza` (путь можно поменять:
   `INSTALL_DIR=/srv/adana-pizza curl ... | sudo bash`);
3. создаст `.env` из `.env.example` со сгенерированным `SESSION_SECRET`;
4. соберёт образы, накатит миграции и запустит сайт;
5. создаст первого админа (`site seed`);
6. установит команду `site` в `/usr/local/bin`;
7. установит systemd-таймер автообновления (проверка GitHub каждые 5 минут).

В конце скрипт выведет адрес сайта и админки. Сразу после — открой
`/opt/adana-pizza/.env` и заполни `SEED_ADMIN_PASSWORD`,
`YANDEX_MAPS_API_KEY` и (если нужна оплата картой) `YOOKASSA_*`, затем:

```bash
site deploy
```

## Команды из консоли

После установки, из любой директории на сервере:

| Команда        | Что делает |
|----------------|------------|
| `site start`   | Поднять сайт (первая сборка образов при первом запуске) |
| `site stop`    | Остановить и удалить контейнеры (данные не трогает) |
| `site restart` | Перезапустить контейнеры на месте |
| `site status`  | Статус контейнеров |
| `site logs`    | Логи всех сервисов (`site logs web` — только приложения) |
| `site deploy`  | Подтянуть последний коммит из GitHub, пересобрать, применить миграции, перезапустить |
| `site seed`    | Разовое создание админ-аккаунта (безопасно перезапускать) |
| `site backup`  | Сохранить БД и загруженные фото в `./backups/*.tar.gz` |

Если репозиторий уже склонирован вручную (без `install.sh`), эти же команды
доступны как `./bin/site <команда>` из корня проекта.

## Автообновление с GitHub

`scripts/auto-update.sh` каждые 5 минут (через systemd-таймер
`adana-autoupdate.timer`) сравнивает локальный HEAD с `origin/main` через
`git ls-remote` — без лишних `git fetch`, если изменений нет. Если появился
новый коммит — вызывает `site deploy` (git reset --hard на новый коммит,
пересборка образов, миграции, перезапуск).

Проверить, что таймер жив:
```bash
systemctl status adana-autoupdate.timer
journalctl -u adana-autoupdate -f
# или
tail -f /opt/adana-pizza/logs/auto-update.log
```

Отключить автообновление: `systemctl disable --now adana-autoupdate.timer`.

**Важно:** директория установки (`/opt/adana-pizza`) должна оставаться
зеркалом GitHub-репозитория — `site deploy` делает `git reset --hard`, так
что любые правки прямо на сервере (не через git push) будут затёрты при
следующем автообновлении. `.env`, `backups/` и данные в Docker-томах это не
затрагивает — они не отслеживаются git.

Если после автообновления деплой упал (например, «плохой» коммit не
собрался) — сайт продолжает работать на предыдущем образе (контейнеры не
трогаются, пока новая сборка не прошла успешно), но локальный HEAD уже
переключён на этот коммит, поэтому таймер не будет повторять попытку с ним
же — почини форвард-фиксом (новым коммитом) и запушь его.

## HTTPS с доменом

Пока `SITE_DOMAIN` не задан, Caddy отдаёт сайт по обычному HTTP на порту 80
— этого достаточно, чтобы сразу зайти на `http://<ip-сервера>/`. Как только
домен указывает на этот сервер:

1. В `.env` пропиши `SITE_DOMAIN="yourdomain.ru"`.
2. `site restart` — Caddy сам получит сертификат Let's Encrypt и с этого
   момента будет отдавать HTTPS с редиректом с HTTP.

## Почему нет прямого порта у контейнера приложения

`X-Forwarded-For` используется для лимита попыток входа в админку (защита от
подбора пароля) — этому заголовку можно доверять только если его выставляет
доверенный прокси перед приложением, а не сам клиент. Поэтому наружу торчит
только Caddy (который сначала стирает то, что прислал клиент, и подставляет
реальный IP — см. `Caddyfile`), а контейнер `web` доступен только изнутри
docker-сети. `TRUSTED_PROXY_HOPS=1` в `docker-compose.yml` явно говорит
приложению, что перед ним ровно один доверенный прокси.

## Резервные копии

```bash
site backup
```

Кладёт `backups/db-<дата>.sql.gz` (`pg_dump` из Postgres, снятый пока сайт
продолжает работать) и `backups/uploads-<дата>.tar.gz` (фото блюд) в
директорию проекта. Скопируй их куда-то за пределы сервера (S3, второй
сервер и т.д.) — локальная копия не защищает от потери самого сервера.

Восстановление БД — руками:
```bash
gunzip -c backups/db-<дата>.sql.gz | docker compose exec -T postgres \
  psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"
```
(значения `POSTGRES_USER`/`POSTGRES_DB` — из `.env`; по умолчанию `adana` /
`adana_pizza`). Redis не бэкапится — он хранит только кеш и счётчики
rate-limit'а, ничего, что нельзя пережить заново.

## Ручной деплой без install.sh

Если репозиторий уже есть на сервере (склонирован вручную):

```bash
cd /path/to/repo
cp .env.example .env   # и заполнить секреты
chmod +x bin/site scripts/auto-update.sh
./bin/site start
./bin/site seed
```

Автообновление руками (без install.sh) — скопировать
`deploy/adana-autoupdate.service` и `.timer` в `/etc/systemd/system/`,
заменив `__REPO_DIR__` на реальный путь, затем:
```bash
systemctl daemon-reload
systemctl enable --now adana-autoupdate.timer
```

## Диагностика

- `site status` — не поднялся какой-то контейнер?
- `site logs web` — ошибки самого приложения.
- `site logs migrate` — миграция базы упала (сайт не запустится, пока не
  почините).
- `curl http://localhost/api/health` на самом сервере — быстрая проверка,
  что приложение и база живы.
